# ASSET PIPELINE

## The short version

**There is no asset pipeline, because there are no assets.**

Every mesh, texture, animation and sound in this game is generated by code at
runtime. The repository contains no `.png`, `.jpg`, `.fbx`, `.glb`, `.wav`,
`.mp3`, `.ttf` or any other binary art file.

---

## Why

Two constraints drove this, and it turned out to be the right answer for both.

**Blender was not available.** The brief allowed for driving Blender with Python
to generate modular armour, rocks, gravestones, ruined walls, wooden props,
dungeon pieces and weapon variations — and said that if Blender were
unavailable, the project should not stall, but should build visually coherent
placeholders from primitive and procedural meshes while keeping the interfaces
needed to replace them later. Blender is not installed in the build environment,
so that fallback applies.

**The budget is zero and licensing had to be airtight.** The brief requires every
external resource to be free and legally usable, with a recorded source,
author, licence, URL, date and list of modifications, and forbids anything whose
licence is uncertain. Generating everything sidesteps the question entirely:
there is nothing to license, nothing to attribute, and the game cannot be an
"asset flip" because there are no third-party assets to flip.

## How each asset class is produced

### Meshes

| Kind | Where | Approach |
| --- | --- | --- |
| Character | `render/geometry/character.ts` | Nested joint groups; body parts from boxes, cylinders and spheres scaled by a per-archetype `BodySpec` |
| Equipment | `render/geometry/equipment.ts` | One builder per module, parameterised by the item's `VisualSpec` (module, tier, material, bulk, spikes, length, accent) |
| Enemies | `render/geometry/enemies.ts` | Seven body plans, each hand-composed for a distinct outline |
| Props | `render/geometry/props.ts` | ~50 builders, each seeded so twenty gravestones are twenty different gravestones |
| Terrain | `render/terrain.ts` | Merged `BufferGeometry` built directly from the navigation grid |

Irregularity matters: `roughBox` jitters box vertices, because nothing in this
world was machine-made.

### Textures

`render/textures.ts` paints into an offscreen `<canvas>` at boot and uploads the
result as a `CanvasTexture`. Each generator produces albedo **and** a correlated
roughness map. Tileable value noise is summed over four octaves with a wrapped
lattice so there is no seam.

Generators: `metalSurface`, `leatherSurface`, `clothSurface`, `woodSurface`,
`stoneSurface`, `groundSurface`, `boneSurface`, `skinSurface`, plus
`radialSprite` and `splatSprite` for particles and decals.

### Animation

Procedural, in `CharacterRig.update` and `EnemyRig.update`. Poses are functions
of a phase value, damped towards rather than snapped to. Stride frequency is
driven by *actual movement speed*, so feet never skate. Action poses
(anticipation, strike, recovery, cast, dodge, hit, death) are driven by the
simulation's own action progress, so the pose and the damage window cannot
drift apart.

There are no animation files to author, export or ship.

### Audio

`audio/audio.ts` synthesises everything through the WebAudio graph: filtered
noise bursts with per-material envelopes for impacts, oscillators for magic and
UI, a filtered-noise bed with an LFO on the cutoff for wind, a sub drone for the
crypt, and three slow detuned saws through a resonant filter for the music bed.

The brief asks for audible differences between blade-on-flesh, blade-on-armour
and mace-on-armour. Flesh is a short damped thud with no ring; armour is a
bright transient with a metallic partial that rings on; a mace on armour is that
same partial driven lower and much harder. Selection is automatic, from the
damage type, the target's armour value and the weapon category.

### Fonts

System font stacks only — an old-style serif stack for body text and a
monospace stack for numerics. No webfont is downloaded.

## Replacing the generated assets later

The interfaces the fallback was meant to preserve are in place:

- `VisualSpec` (in `sim/items.ts`) is the contract between an item and its mesh.
  Swapping `buildWeapon` for a glTF loader keyed on the same spec requires no
  change to gameplay, data or saves.
- `EnemyVisual` (in `sim/enemyDef.ts`) does the same for enemies.
- `PropKind` (in `world/zoneDef.ts`) is a closed string union; `buildProp` is a
  single lookup that could resolve to loaded models instead of builders.
- `CharacterRig` exposes `setModule(module, spec, seed, category)`. A skinned
  replacement need only satisfy that method plus `setState` and `update`.

The material library (`render/materials.ts`) is already keyed by kind and
colour, so imported models can share it or bring their own without touching
anything else.
